# 평가 대비 설명 자료

이 문서는 기능 확인용 체크리스트가 아니라, 평가에서 프로그램의 구조와 원리를 설명하기 위한 답변 자료이다.

## 코드 구조 및 설계

### 1. MAC 연산의 전체 흐름

사용자 입력 모드에서는 `input_matrix()`가 필터 A, 필터 B, 패턴을 각각 3×3 `Matrix` 객체로 만든다. JSON 모드에서는 `create_matrix()`가 JSON 배열의 행과 열 개수 및 숫자 여부를 검사한 뒤 `Matrix`로 변환한다.

`calculate_mac()`은 먼저 패턴과 필터가 크기가 같은 정방행렬인지 검사한다. 이후 이중 반복문으로 같은 행과 열에 있는 패턴 값과 필터 값을 곱하고, 그 결과를 `score`에 계속 더한다. 모든 위치를 처리하면 누적된 `score`를 반환한다.

예를 들어 두 2×2 행렬에 대해 다음과 같이 계산한다.

```text
pattern = [[1, 2],     filter = [[5, 6],
           [3, 4]]               [7, 8]]

MAC = 1×5 + 2×6 + 3×7 + 4×8 = 70
```

평가에서 짧게 답하면 다음과 같다.

> 입력 데이터를 Matrix로 만든 뒤, 같은 위치의 값을 곱해서 score에 누적하고 최종 합계를 유사도 점수로 반환합니다.

### 2. 패턴 키에서 크기를 추출하고 필터와 연결하는 방법

패턴 키는 `size_N_idx`, 필터 그룹 키는 `size_N` 형식이다. 예를 들어 `size_13_2`라는 패턴 키를 `_`로 분리하면 `size`, `13`, `2`가 된다. `extract_pattern_size()`는 가운데 값인 `13`을 정수로 변환한다.

`analyze_pattern()`은 추출한 크기로 `size_13`이라는 필터 키를 만든 뒤 `filter_groups`에서 해당 크기의 Cross 필터와 X 필터를 가져온다. 따라서 새로운 크기가 추가되어도 키 규칙만 같다면 동일한 로직으로 알맞은 필터를 선택할 수 있다.

> `size_N_idx`에서 N을 추출하고, 그 값으로 `size_N` 키를 만들어 같은 크기의 필터 그룹을 조회하도록 설계했습니다.

### 3. 라벨 정규화를 별도 함수로 분리한 이유

JSON에는 같은 의미의 라벨이 서로 다르게 표현될 수 있다. 이 프로그램에서는 `+`와 `cross`를 `Cross`로, `x`를 `X`로 변환한다. 변환하지 않으면 계산 결과가 `Cross`인데 expected가 `+`인 경우처럼 의미는 같아도 문자열이 달라 FAIL이 될 수 있다.

`normalize_label()`을 별도 함수로 두면 다음 장점이 있다.

- 필터 키와 expected가 동일한 규칙을 사용한다.
- 라벨 처리 코드가 여러 위치에 중복되지 않는다.
- 허용하지 않는 라벨을 한곳에서 검증할 수 있다.
- 새로운 라벨을 지원할 때 `LABELS`와 관련 판정 부분을 중심으로 확장할 수 있다.

> 외부 데이터의 다양한 표현을 내부의 Cross와 X로 통일해 문자열 차이에 의한 오판정을 막고, 변환과 검증 규칙을 한곳에서 관리하기 위해 분리했습니다.

### 4. 시간 측정에서 I/O를 제외한 방법

입력과 JSON 로딩, 결과 출력에는 사용자나 운영체제 상태에 따른 지연이 포함되므로 MAC 성능과 직접 관계가 없다. 따라서 `measure_average_time()`은 행렬이 이미 준비된 상태에서 시작 시간을 기록하고, `calculate_mac()`만 10회 호출한 뒤 종료 시간을 기록한다.

전체 시간을 밀리초로 변환하고 반복 횟수 10으로 나누어 1회 평균 시간을 구한다. 측정에는 `time.perf_counter()`를 사용하며, 출력은 측정이 끝난 뒤 수행한다.

> 입력과 출력은 측정 구간 밖에 두고, 시작 시각과 종료 시각 사이에서 MAC 함수만 10회 실행한 뒤 평균을 계산했습니다.

## 핵심 기술 원리

### 5. MAC 점수가 높을수록 더 유사하다고 판단하는 이유

MAC은 패턴과 필터의 같은 위치에 있는 값을 곱해 모두 더한다. 패턴의 큰 값과 필터의 큰 값이 같은 위치에 많이 겹치면 양의 곱이 많이 누적되어 점수가 커진다. 반대로 모양이 맞지 않으면 필터 값이 0인 위치와 겹치는 경우가 많아 점수가 작아진다.

이 과제의 Cross 필터는 십자 위치에, X 필터는 대각선 위치에 가중치가 있다. 따라서 입력 패턴의 활성 위치가 어느 필터의 활성 위치와 더 많이 일치하는지를 MAC 점수로 비교할 수 있다.

다만 이 해석은 두 필터의 크기와 값의 범위가 비교 가능하게 설계되었다는 전제가 필요하다. 필터마다 전체 가중치 규모가 크게 다르면 모양보다 가중치 크기 때문에 점수가 높아질 수 있으며, 일반적인 시스템에서는 필요에 따라 정규화를 적용한다.

> 같은 위치에서 큰 값끼리 겹칠수록 곱의 누적합이 커지므로, 동일한 기준으로 만든 필터끼리는 MAC 점수가 높은 쪽이 패턴과 더 유사하다고 볼 수 있습니다.

### 6. 연산 횟수가 N²이고 시간 복잡도가 O(N²)인 이유

N×N 행렬에는 원소가 N²개 있다. `calculate_mac()`은 행을 도는 반복문을 N번 실행하고, 각 행마다 열을 도는 반복문을 N번 실행한다. 따라서 곱셈과 누적 덧셈은 각각 N×N번 수행된다.

```text
3×3   →   9개 위치
5×5   →  25개 위치
13×13 → 169개 위치
25×25 → 625개 위치
```

N이 2배가 되면 방문할 원소 수는 약 4배가 된다. 반복문 밖의 검증 비용도 행을 확인하므로 O(N)이지만, 전체에서는 O(N²) 연산이 지배적이다. 메모리 사용량도 행렬 전체를 저장하므로 O(N²)이다.

> N개의 행마다 N개의 열을 모두 방문하므로 총 N²번 MAC을 수행하며, 따라서 시간 복잡도는 O(N²)입니다.

### 7. 부동소수점 오차와 epsilon이 필요한 이유

컴퓨터의 `float`는 숫자를 2진 부동소수점으로 저장한다. `0.1`처럼 2진수로 유한하게 표현되지 않는 값은 제한된 비트 안에 근삿값으로 저장된다. 이 근삿값을 여러 번 곱하고 더하면 아주 작은 오차가 누적될 수 있다.

예를 들어 수학적으로 같은 점수라도 실제 계산 결과가 다음처럼 나올 수 있다.

```text
0.9000000000000000
0.8999999999999999
```

이를 단순히 `==` 또는 대소 비교하면 의미 없는 미세한 차이로 승자를 정하게 된다. 이 프로그램은 두 점수 차이의 절댓값이 `1e-9`보다 작으면 사실상 같은 값으로 보고 동점 처리한다.

```python
if abs(first_score - second_score) < EPSILON:
    return undecided_label
```

> 일부 10진 소수는 2진수로 정확히 저장되지 않아 계산 오차가 생깁니다. 그래서 두 값의 정확한 일치가 아니라 차이가 허용오차보다 작은지를 검사해 동점을 판정합니다.

### 8. 모드 1과 모드 2의 동점 표시가 다른 이유

두 모드 모두 동일한 `judge()` 함수와 동일한 epsilon 정책을 사용하므로 수치 판정 기준은 같다. 다른 것은 반환하는 동점 라벨뿐이다.

- 모드 1은 사용자에게 보여 주는 한국어 결과이므로 `판정 불가`를 전달한다.
- 모드 2는 JSON 결과 규칙에 맞춰 영문 표준 라벨인 `UNDECIDED`를 전달한다.
- 모드 2의 expected는 `Cross` 또는 `X`로 정규화되므로, 판정이 `UNDECIDED`이면 expected와 다르게 되어 FAIL로 집계된다.

즉, 알고리즘이 다른 것이 아니라 출력 대상과 요구 형식에 맞게 표시 문자열만 다르게 주입한 것이다.

> 두 모드의 epsilon 기준은 같고, 사용자 입력 모드는 한국어인 `판정 불가`, JSON 모드는 데이터 규격에 맞는 `UNDECIDED`를 사용합니다.

## 심층 인터뷰 대비

### 9. 새로운 라벨 `o`를 추가하는 확장 순서

먼저 `o`의 의미와 이에 대응하는 필터가 무엇인지 데이터 규칙을 정의해야 한다. 그다음 아래 순서로 확장한다.

1. `LABELS`에 외부 표현 `o`와 내부 표준 라벨 `O`의 매핑을 추가한다.
2. 필터 그룹 검증이 Cross와 X만 요구하는 현재 구조를 수정하여 O 필터도 읽도록 한다.
3. `analyze_pattern()`에서 O 필터의 MAC 점수도 계산한다.
4. 현재 두 점수만 비교하는 `judge()`를 여러 `(라벨, 점수)`을 비교할 수 있는 구조로 확장한다.
5. 최고 점수가 여러 개인 경우 epsilon 정책으로 `UNDECIDED`를 반환하도록 한다.
6. 결과 딕셔너리와 콘솔 출력에 O 점수를 추가한다.
7. `o` 패턴, 대소문자, 잘못된 라벨, O와 다른 필터의 동점 사례를 테스트한다.

정규화만 추가하면 입력은 읽을 수 있어도 O 점수를 계산하거나 판정할 수 없으므로, 데이터 규칙부터 출력과 테스트까지 함께 확장해야 한다.

> 라벨 규칙을 먼저 정의하고 정규화, 필터 로딩, 점수 계산, 다중 후보 판정, 출력, 테스트 순서로 확장하겠습니다.

### 10. 1000×1000 패턴 처리 시 문제와 최적화

1000×1000 행렬 하나에는 원소가 100만 개 있다. 패턴과 여러 필터를 파이썬의 중첩 리스트와 개별 `float` 객체로 저장하면 실제 메모리 사용량이 단순한 8MB보다 훨씬 커진다. 순수 파이썬 이중 반복문도 원소 접근과 함수 호출을 100만 번 수행하므로 느려진다. 필터 수와 반복 측정 횟수가 늘어나면 비용도 그만큼 증가한다.

최적화 우선순위는 다음과 같다.

1. 실무 조건이라면 NumPy 같은 연속 메모리 기반 배열과 벡터화 연산을 사용한다.
2. 값이 대부분 0이라면 0이 아닌 위치만 저장하는 희소 표현을 사용한다.
3. 반복문을 유지해야 한다면 `get_value()` 호출을 매번 하지 않고 행 리스트를 지역 변수로 가져와 접근 비용을 줄인다.
4. 여러 필터를 처리한다면 데이터 재사용과 캐시 효율을 고려하고 병렬 처리를 검토한다.
5. 전체 데이터가 메모리에 들어오지 않는다면 행 또는 블록 단위로 나누어 스트리밍 처리한다.

알고리즘상 모든 원소를 확인해야 한다면 밀집 행렬의 O(N²) 자체는 피하기 어렵지만, 구현 방식과 데이터 특성을 이용해 상수 비용 또는 실제 방문 원소 수를 줄일 수 있다.

> 1000×1000은 행렬당 100만 개 원소라 순수 파이썬 반복문과 객체 기반 저장의 시간·메모리 비용이 커집니다. 우선 연속 배열과 벡터화를 적용하고, 데이터가 희소하면 0이 아닌 값만 계산하겠습니다.

### 11. CPU 직렬 처리와 NPU 병렬 처리의 병목

CPU에서 현재 코드처럼 실행하면 각 원소의 곱셈과 덧셈을 반복문으로 순서대로 처리한다. 특히 파이썬에서는 반복문, 메서드 호출, 객체 접근 비용이 실제 산술 연산보다 크게 작용할 수 있다. 대규모 행렬에서는 연산량뿐 아니라 데이터를 메모리에서 CPU로 가져오는 메모리 대역폭과 캐시 미스도 병목이 된다.

NPU는 많은 곱셈기와 누산기를 이용해 여러 MAC을 동시에 처리하도록 설계되어 있다. 따라서 대규모의 규칙적인 행렬 연산에서 높은 처리량을 낼 수 있다. 그러나 NPU도 무조건 빠른 것은 아니다. 데이터를 NPU 메모리로 전송하는 시간, 제한된 온칩 메모리, 메모리 대역폭, 작업을 작은 단위로 나누고 결과를 합치는 비용이 병목이 될 수 있다. 행렬이 너무 작으면 전송과 준비 비용이 연산 절감보다 클 수도 있다.

```text
CPU: 범용성과 복잡한 제어에 강하지만 대량 MAC의 직렬 반복이 병목
NPU: 대량 MAC 병렬 처리에 강하지만 데이터 이동과 메모리 대역폭이 병목
```

> CPU에서는 순차 반복과 객체 접근 비용이 주요 병목이고, NPU는 MAC을 병렬화해 계산 병목을 줄입니다. 규모가 커지면 NPU에서도 연산기보다 데이터 공급 속도와 메모리 이동이 병목이 될 수 있습니다.
